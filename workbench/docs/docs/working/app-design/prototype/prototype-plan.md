# Prototype Implementation Plan: ASH Workbench UI Skeleton POC

## 1. Executive Summary

Build a UI skeleton proof-of-concept for the ASH Workbench VS Code extension that demonstrates native VS Code UI (activity bar, tree view) and a React/ShadCN WebView, using mock data exclusively. No database, no ASH CLI, no real scanning.

**Key architectural decisions (from research):**
- Sibling layout: `webview/` and `vsix/` as siblings under `workbench/`, bridged by a copy step (`webview/dist/` to `vsix/webview-dist/`)
- Dual WebView contexts (Option B): sidebar `WebviewViewProvider` for compact dashboard, editor-area `WebviewPanel` for full-width Finding List and Finding Detail
- Same Vite-built React app loaded in both contexts, differentiated by an `init` message
- Tailwind CSS v4, ShadCN/ui, React 19, Vite 8
- Independent npm installs per package (no Yarn workspaces)

**Reference:** `docs/docs/working/app-design/prototype/prototype-research.md` -- all architectural analysis, API references, and risk mitigations.

---

## 2. What Will Be Done

- Configure Vite build output (fixed filenames, no code splitting) and the copy step from `webview/dist/` to `vsix/webview-dist/`
- Restructure `vsix/src/` into modules: commands/, providers/, models/, mock/
- Define TypeScript types for data model and message protocol
- Create mock data covering all scan statuses, severity levels, and disposition states
- Declare view container, views, commands, and activation events in `vsix/package.json`
- Implement `ScanTreeProvider` (`TreeDataProvider`) with mock scan history
- Install Tailwind v4 and ShadCN/ui in `webview/`, map VS Code theme variables
- Implement `SidebarWebviewProvider` and `FindingsPanelManager` (dual WebView contexts)
- Build typed `postMessage` bridge between extension host and React app
- Build sidebar dashboard: triage summary, severity counts, "Run Scan" button
- Build editor panel screens: Finding List (table, filters, badges) and Finding Detail (code snippet, disposition controls)
- Wire code navigation (`vscode.window.showTextDocument`)
- Update launch configuration, `.vscodeignore`, and build scripts

## 3. What Will NOT Be Done

- PGLite/Prisma database integration
- ASH CLI spawning, SARIF parsing, or real scanning
- Data persistence across sessions
- AI-enriched explanations or fix suggestions
- Batch triage or suppression file generation
- Delta reports between scan runs
- Yarn workspaces or monorepo tooling
- Production-grade error handling or telemetry
- Automated test suite (manual verification only for POC)

### Phase 0: Build Pipeline -- Completed

Establish the build bridge between sibling packages before writing any application code. This catches build issues immediately.

**Steps:**

1. **Configure Vite output** -- Edit `webview/vite.config.ts`: add `build.rollupOptions.output` with `entryFileNames: 'assets/index.js'`, `assetFileNames: 'assets/[name].[ext]'`, disable code splitting. 2. **Add copy scripts to vsix** -- Edit `vsix/package.json` scripts:
   - `"copy:webview": "cp -r ../webview/dist ./webview-dist"`

   - `"build": "npm run build:webview && npm run compile"`
   - `"vscode:prepublish": "npm run build"`

3. **Gitignore the copy target** -- Add `webview-dist/` to `vsix/.gitignore`.

4. **Update `.vscodeignore`** -- Ensure `webview-dist/` is NOT excluded. Add `!webview-dist/**` as a safety include.

5. **Verify end-to-end** -- Run `cd vsix && npm run build`. Confirm `vsix/webview-dist/assets/index.js` exists with the Vite scaffold content. Delete `vsix/webview-dist/` and re-run to confirm reproducibility.

**Exit criteria:** `npm run build` in `vsix/` produces both `out/` (tsc) and `webview-dist/` (Vite copy) without errors.

## 6. KISS Decisions (All Adopted)

### 6.1 Single React App, Not Two -- ADOPTED

Load the exact same Vite bundle in both sidebar and editor panel. Use a context discriminant (`init` message) to pick which root component to render. No separate builds, no separate entry points. One build, one copy, one set of dependencies. Sidebar loads the full bundle but the bundle is small enough that this doesn't matter for POC.

### 6.2 Static Mock Data (No Simulation) -- ADOPTED

Mock data is a static TypeScript module. No timers, no random generation, no state machines simulating scan progress. The "RUNNING" scan is just a static object. Eliminates timing-related bugs and simplifies the prototype to pure UI rendering.

### 6.3 In-Memory Disposition State -- ADOPTED

Disposition changes update a JavaScript object in the extension host's memory. No persistence. Reloading the extension resets all dispositions to mock defaults. The data flow pattern (WebView sends action, extension host updates, extension host pushes state back) is identical to what the production version will use -- only the storage layer changes later.

### 6.4 Copy Step Over Monorepo Tooling -- ADOPTED

Bridge the sibling gap with `cp -r` instead of Yarn workspaces, npm link, or shared packages. Zero configuration overhead. One extra terminal for watch mode, acceptable for a prototype.

### 7.2 Message Protocol Types

```typescript
// vsix/src/models/messages.ts

import type { ScanSummary, FindingRow, DispositionSummary, Disposition } from './types';

// Extension Host → WebView
export type ExtToWebviewMessage =
  | { type: 'init'; payload: { context: 'sidebar' } }
  | { type: 'init'; payload: { context: 'editorPanel'; scanId: string } }
  | { type: 'stateUpdate'; payload: { scans: ScanSummary[]; summary: DispositionSummary } }
  | { type: 'findingsUpdate'; payload: { scanId: string; findings: FindingRow[] } }
  | { type: 'findingDetail'; payload: FindingRow }
  | { type: 'dispositionUpdated'; payload: { findingId: string; disposition: Disposition } };

// WebView → Extension Host
export type WebviewToExtMessage =
  | { type: 'requestState' }
  | { type: 'selectScan'; payload: { scanId: string } }
  | { type: 'selectFinding'; payload: { findingId: string } }
  | { type: 'setDisposition'; payload: { findingId: string; disposition: Disposition } }
  | { type: 'navigateToCode'; payload: { filePath: string; startLine: number } }
  | { type: 'startScan' }
  | { type: 'openFindings'; payload: { scanId: string } };
```

### 7.3 Shared WebView HTML Generator

```typescript
// vsix/src/providers/webviewHtml.ts
import * as vscode from 'vscode';

export function getWebviewHtml(webview: vscode.Webview, extensionUri: vscode.Uri): string {
  const scriptUri = webview.asWebviewUri(
    vscode.Uri.joinPath(extensionUri, 'webview-dist', 'assets', 'index.js')
  );
  const styleUri = webview.asWebviewUri(
    vscode.Uri.joinPath(extensionUri, 'webview-dist', 'assets', 'index.css')
  );
  const nonce = getNonce();

  return `<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src ${webview.cspSource} 'unsafe-inline'; script-src 'nonce-${nonce}'; font-src ${webview.cspSource}; img-src ${webview.cspSource};">
  <link rel="stylesheet" href="${styleUri}">
  <title>ASH Workbench</title>
</head>
<body>
  <div id="root"></div>
  <script nonce="${nonce}" src="${scriptUri}"></script>
</body>
</html>`;
}

function getNonce(): string {
  let text = '';
  const possible = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  for (let i = 0; i < 32; i++) {
    text += possible.charAt(Math.floor(Math.random() * possible.length));
  }
  return text;
}
```

### 7.4 useVSCodeAPI Hook

```typescript
// webview/src/hooks/useVSCodeAPI.ts
import { useEffect } from 'react';
import type { WebviewToExtMessage, ExtToWebviewMessage } from '../types/messages';

const vscode = acquireVsCodeApi();

export function postMessage(message: WebviewToExtMessage): void {
  vscode.postMessage(message);
}

export function useMessages(handler: (msg: ExtToWebviewMessage) => void): void {
  useEffect(() => {
    const listener = (event: MessageEvent<ExtToWebviewMessage>) => handler(event.data);
    window.addEventListener('message', listener);
    return () => window.removeEventListener('message', listener);
  }, [handler]);
}
```

### 7.5 Context-Aware App Root

```typescript
// webview/src/App.tsx (structure)
import { useReducer, useCallback, useEffect } from 'react';
import { postMessage, useMessages } from './hooks/useVSCodeAPI';
import { SidebarDashboard } from './components/SidebarDashboard';
import { FindingList } from './components/FindingList';
import { FindingDetail } from './components/FindingDetail';
import type { ExtToWebviewMessage } from './types/messages';

// State and reducer defined here...

function App() {
  const [state, dispatch] = useReducer(reducer, initialState);

  const handleMessage = useCallback((msg: ExtToWebviewMessage) => {
    dispatch({ type: 'MESSAGE', payload: msg });
  }, []);

  useMessages(handleMessage);

  useEffect(() => {
    postMessage({ type: 'requestState' });
  }, []);

  if (state.context === 'sidebar') {
    return <SidebarDashboard state={state} />;
  }

  if (state.view === 'findingDetail' && state.selectedFinding) {
    return <FindingDetail finding={state.selectedFinding} />;
  }

  return <FindingList findings={state.findings} filters={state.filters} />;
}
```

### 7.6 FindingsPanelManager (Reuse Pattern)

```typescript
// vsix/src/providers/findingsPanelManager.ts (structure)
import * as vscode from 'vscode';
import { getWebviewHtml } from './webviewHtml';

export class FindingsPanelManager {
  private panel: vscode.WebviewPanel | undefined;

  constructor(private readonly extensionUri: vscode.Uri) {}

  public showFindings(scanId: string): void {
    if (this.panel) {
      this.panel.reveal(vscode.ViewColumn.One);
      this.panel.webview.postMessage({ type: 'init', payload: { context: 'editorPanel', scanId } });
      return;
    }

    this.panel = vscode.window.createWebviewPanel(
      'ashWorkbench.findingsPanel',
      'ASH Findings',
      vscode.ViewColumn.One,
      {
        enableScripts: true,
        localResourceRoots: [vscode.Uri.joinPath(this.extensionUri, 'webview-dist')],
      }
    );

    this.panel.webview.html = getWebviewHtml(this.panel.webview, this.extensionUri);
    this.panel.webview.postMessage({ type: 'init', payload: { context: 'editorPanel', scanId } });

    this.panel.webview.onDidReceiveMessage(/* handler */);
    this.panel.onDidDispose(() => { this.panel = undefined; });
  }
}
```

## 8. Testing Strategy

The prototype uses **manual verification only**. No automated test suite.

### Per-Phase Verification

| Phase | Verification Method |
|-------|-------------------|
| 0 (Build Pipeline) | `npm run build` in vsix/ succeeds. `webview-dist/` contains expected files. |
| 1 (Extension Skeleton) | F5 launch. Activity bar icon visible. Commands in palette. |
| 2 (Tree View) | Scans visible in sidebar tree with correct icons, labels, descriptions. Click stores selection. |
| 3 (WebView Setup) | `npm run build` in webview/ produces correct output. ShadCN components import without errors. |
| 4 (Message Bridge) | F5 launch. Sidebar loads React. Click scan in tree opens editor panel. Console.log confirms messages. |
| 5 (UI Screens) | Visual inspection of all screens. Click-through of all interactions. Both themes. |
| 6 (Polish) | Full exit criteria checklist. `vsce ls` shows correct packaging. |

### Critical Manual Tests

1. **Cold start:** Close all VS Code windows. Open the workspace. Verify extension activates and sidebar renders.
2. **Theme switch:** Switch between light/dark themes while the extension is open. Verify colors update.
3. **Panel lifecycle:** Open editor panel. Close the tab. Reopen via tree click. Verify state is fresh.
4. **Sidebar collapse:** Collapse the sidebar. Switch to another activity bar icon. Switch back. Verify sidebar WebView re-renders with data.

# Docusaurus Documentation System Research

## Overview

This document analyzes the current Docusaurus setup for the ASH Workbench project and designs a scalable, self-organizing documentation architecture. The goal is a system where three distinct documentation audiences (developers, users, AI working docs) are served through separate navigation sections, and where adding a new page requires zero configuration changes -- just drop a markdown file in the right directory.

The current site is a near-stock Docusaurus v3.9.2 classic template. Nearly everything needs to change from the default template to support the desired architecture.

## Architecture

### Current State

The Docusaurus site lives at `docs/` within the workbench monorepo:

```
workbench/
  ash-workbench/       # VS Code extension source
  docs/                # Docusaurus project root
    docs/              # Content directory (Docusaurus convention)
      intro.md         # Stock template page (to be removed)
      developer-docs/  # Empty directory
      user-docs/       # Empty directory
      working/         # Empty directory with nested docs/
    docusaurus.config.ts
    sidebars.ts
    src/               # React source (homepage, components, CSS)
    static/            # Static assets (images, favicon)
    package.json       # Docusaurus v3.9.2, React 19
```

**Key observations about current config:**

| Setting | Current Value | Issue |
|---|---|---|
| `title` | `"My Site"` | Template placeholder |
| `tagline` | `"Dinosaurs are cool"` | Template placeholder |
| `url` | `"https://your-docusaurus-site.example.com"` | Placeholder |

### Proposed Architecture

**Single docs plugin, three autogenerated sidebars.** This is the simplest approach that meets all requirements.

```
                    docusaurus.config.ts
                           |
                      sidebars.ts
                     /     |        \
          userDocsSidebar  devDocsSidebar  workingSidebar
               |                |               |
          user-docs/      developer-docs/    working/
          (autogen)        (autogen)         (autogen)
```

**Why single plugin + multi-sidebar (not multi-instance)?**

| Approach | Pros | Cons |
|---|---|---|
| **Single plugin + multi-sidebar** | Simple config, one `sidebars.ts`, easy cross-linking between sections, all content in one `docs/` dir | All sections share `/docs/` URL prefix |
| Multi-instance plugins | Clean URL separation (`/user-docs/`, `/dev-docs/`) | Multiple config files, harder cross-linking, more boilerplate, each instance needs separate sidebar file |

The single plugin approach wins for a documentation system that prioritizes simplicity and AI-agent writability. Cross-linking between developer and user docs is common and trivial with one plugin. The shared URL prefix (`/docs/user-docs/...`, `/docs/developer-docs/...`) is a reasonable tradeoff.

### Alternative: Multi-Instance Approach (for reference)

If URL separation becomes important later, the multi-instance approach would use:

```ts
// docusaurus.config.ts
plugins: [
  ['@docusaurus/plugin-content-docs', {
    id: 'user-docs',
    path: 'user-docs',          // separate content dir
    routeBasePath: 'user-docs', // /user-docs/ URL prefix
    sidebarPath: './sidebars-user.ts',
  }],
  ['@docusaurus/plugin-content-docs', {
    id: 'developer-docs',
    path: 'developer-docs',
    routeBasePath: 'developer-docs',
    sidebarPath: './sidebars-dev.ts',
  }],
  // ...
]
```

This is not recommended at this stage due to added complexity, but could be migrated to later if needed.

## Detailed Findings

### Self-Organizing Sidebar Mechanics

Docusaurus autogenerated sidebars (`{type: 'autogenerated', dirName: '...'}`) work as follows:

1. **Files**: Every `.md` / `.mdx` file in the target directory tree becomes a sidebar item
2. **Directories**: Every subdirectory becomes a collapsible category
3. **Ordering**: Items sort by `sidebar_position` frontmatter (ascending), then alphabetically by filename
4. **Category metadata**: Controlled by `_category_.json` files in each directory
5. **Category index**: `README.md`, `index.md`, or a file matching the directory name automatically becomes the category's clickable index page

**This means adding a new page requires only:**
1. Create a `.md` file in the correct directory with `title` frontmatter
2. Optionally set `sidebar_position` to control ordering
3. That's it. No config files to update.

**Adding a new sub-section requires:**
1. Create a new subdirectory
2. Add a `_category_.json` with `label` and `position`
3. Optionally add a `README.md` for the category overview
4. Add `.md` content files

### README.md as "Overview" Convention

Docusaurus v3 natively supports README.md as a category index. When `README.md` exists in a directory that maps to a sidebar category:

- The category label in the sidebar becomes a clickable link
- Clicking it navigates to the README.md content
- The README.md does **not** appear as a separate item under the category

For the **top-level** README.md in each section (e.g., `user-docs/README.md`), the behavior is different -- it appears as a regular sidebar item since there's no parent category to attach to. To make it display as "Overview" at the top:

```yaml
---
title: Overview
sidebar_label: Overview
sidebar_position: 1
---
```

For **subdirectory** README.md files (e.g., `user-docs/getting-started/README.md`), the file automatically becomes the category index. The `title` frontmatter controls what appears in the content area:

```yaml
---
title: Overview
---
```

No `sidebar_position` needed for category indices since the category index is inherently the "cover page" for the category.

### Docusaurus Config Changes Required

The following changes are needed in `docusaurus.config.ts`:

| Area | Change | Details |
|---|---|---|
| `title` | Update | Change from `"My Site"` to project name (e.g., `"ASH Workbench"`) |
| `tagline` | Update | Change from template text to project description |
| `url` | Update | Set to actual deployment URL |
| `organizationName` | Update | Set to actual GitHub org |
| `projectName` | Update | Set to actual repo name |
| `editUrl` | Update | Point to actual repo's docs directory |
| `onBrokenLinks` | Consider `'warn'` | During early development, `'throw'` will fail builds on any broken link. Switch to `'warn'` initially, tighten to `'throw'` for production. |
| `navbar.items` | Replace | Remove "Tutorial", add three `docSidebar` entries |
| `footer.links` | Replace | Remove Docusaurus community links, add project-relevant links |
| Blog preset | Disable | Set `blog: false` in classic preset options |
| Mermaid | **Enable** | Add `@docusaurus/theme-mermaid` -- Mermaid diagrams are preferred over static images |

### Disabling Blog

The blog plugin is enabled by default in the classic preset. To disable:

```ts
presets: [
  [
    'classic',
    {
      docs: {
        sidebarPath: './sidebars.ts',
        editUrl: 'https://github.com/YOUR_ORG/YOUR_REPO/tree/main/workbench/docs/',
      },
      blog: false, // Disable blog
      theme: {
        customCss: './src/css/custom.css',
      },
    } satisfies Preset.Options,
  ],
],
```

### Enabling Mermaid (Required)

Mermaid diagrams are the preferred way to represent visual information (architecture diagrams, flow charts, sequence diagrams, state machines, ER diagrams). Where possible, documentation should use Mermaid over static images -- Mermaid renders natively in Docusaurus, is version-controllable as text, and is easy for both humans and AI agents to author and maintain. To enable:

1. Install: `npm install @docusaurus/theme-mermaid`
2. Add to config:

```ts
const config: Config = {
  // ...
  markdown: {
    mermaid: true,
  },
  themes: ['@docusaurus/theme-mermaid'],
  // ...
};
```

## Patterns and Conventions

### File Naming

- **Kebab-case** for all filenames: `getting-started.md`, `system-overview.md`
- **README.md** (uppercase) for category overview/index pages
- **`_category_.json`** in every subdirectory (Docusaurus convention)

### Frontmatter Convention

**Minimum required frontmatter for every document:**

```yaml
---
title: Human-Readable Page Title
---
```

**README.md files (top-level section overviews):**

```yaml
---
title: Overview
sidebar_label: Overview
sidebar_position: 1
---
```

**README.md files (subdirectory category indices):**

```yaml
---
title: Overview
---
```

No `sidebar_position` needed for category indices since the category index is inherently the "cover page" for the category.

**Regular pages (optional positioning):**

```yaml
---
title: Installation Guide
sidebar_position: 2
---
```

If `sidebar_position` is omitted, pages sort alphabetically by filename. This is acceptable for most content and reduces maintenance burden.

### `_category_.json` Template

```json
{
  "label": "Category Name",
  "position": 1,
  "collapsible": true,
  "collapsed": true,
  "link": {
    "type": "generated-index",
    "description": "Brief description of this category."
  }
}
```

If a README.md exists in the directory, change `link` to:

```json
{
  "link": {
    "type": "doc",
    "id": "path/to/README"
  }
}
```

Or simply omit the `link` property entirely -- Docusaurus auto-detects README.md as the category index.

### AI Agent Workflow for Adding Documentation

**Adding a user doc:**
1. Create `docs/docs/user-docs/<topic-or-subdir>/<filename>.md`
2. Add `title` frontmatter
3. Done. Autogenerated sidebar picks it up.

**Adding a developer doc:**
1. Create `docs/docs/developer-docs/<topic-or-subdir>/<filename>.md`
2. Add `title` frontmatter
3. Done.

**Creating a new sub-section:**
1. Create the directory: `docs/docs/<section>/<new-subdir>/`
2. Create `_category_.json` with `label` and `position`
3. Create `README.md` with `title: Overview`
4. Add content `.md` files

**Adding a working doc:**
1. Create `docs/docs/working/<topic-subdir>/<filename>.md`
2. Add `title` frontmatter
3. Done.

### Content Guidelines by Audience

**Developer Docs** should follow this structure per topic:

```markdown
---
title: <Topic Name>
---

# <Topic Name>

Brief orientation: what this is and why it exists.

## How It Works

Concise explanation of the implementation. Include code snippets where helpful.

## Usage

How to use/interact with this from a developer perspective. Examples.

## Extending / Maintaining

What a developer needs to know to modify this. Key files, patterns, gotchas.

## Known Issues

Current limitations, workarounds, planned improvements.

## References

Links to related docs, external resources, relevant source files.
```

**User Docs** should follow this structure per feature:

```markdown
---
title: <Feature Name>
---

# <Feature Name>

What this feature does and why it helps you.

## Getting Started

Step-by-step instructions to use the feature.

## Tips and Best Practices

How to get the most out of this feature.

## Troubleshooting

Common issues and their solutions.

## Related Features

Links to other features that complement this one.
```

## Issues and Risks

### Naming Discrepancy

The user's request references `docs/develop-docs/` but the actual directory on disk is `docs/docs/developer-docs/`. This should be standardized. **Recommendation:** Use `developer-docs` as it is more grammatically clear and already exists on disk.

### Template Artifacts to Remove

The following stock template content should be removed or replaced:

| File/Config | Action |
|---|---|
| `docs/docs/intro.md` | **Remove** -- template content, not in any section |
| `src/pages/markdown-page.md` | **Remove** -- template page |
| `src/components/HomepageFeatures/` | **Replace** -- stock Docusaurus features section |
| `src/pages/index.tsx` | **Update** -- replace template homepage content |
| `static/img/undraw_*` | **Remove** -- template illustrations |
| `static/img/docusaurus-social-card.jpg` | **Replace** with project social card |
| `static/img/docusaurus.png` | **Remove** |

### Empty Directories

Git does not track empty directories. The currently empty `developer-docs/` and `user-docs/` directories will not persist in version control until files are added. Adding `_category_.json` and `README.md` files to each solves this and is needed anyway.

### Build Failures on Empty Sidebars

If a sidebar's `dirName` contains no markdown files, the Docusaurus build may warn or fail. Each section should have at least one document (the README.md overview) to prevent this.

### Working Docs in Production

The `working/` directory contains ephemeral AI research and planning docs. Consider whether these should be:
- **Included in production builds** (current path -- they show in the sidebar)
- **Excluded from production builds** via `.docusaurusignore` or build-time filtering
- **Visually distinguished** (e.g., with an admonition banner or different styling)

If working docs should be excluded from production, a build-time environment variable could conditionally include the `workingSidebar` and navbar item.

### Cross-Linking Between Sections

With the single-plugin approach, cross-linking is straightforward:

```markdown
See the [Installation Guide](/docs/user-docs/getting-started/installation) for setup instructions.
```

Or using Docusaurus file path references:

```markdown
See the [Installation Guide](../user-docs/getting-started/installation.md) for setup instructions.
```

The second form is preferred as Docusaurus validates file paths at build time.

## Key Takeaways

1. **Three sidebars, one plugin** -- The multi-sidebar approach with autogenerated content from `dirName` is the simplest architecture that meets all requirements.

2. **Self-organization is native** -- Docusaurus autogenerated sidebars handle self-organization out of the box. New files appear automatically. The only convention to enforce is proper frontmatter.

3. **README.md = Overview** -- Docusaurus natively treats README.md as category indices. Combined with `title: Overview` frontmatter, this satisfies the convention with no configuration.

4. **AI agents need minimal knowledge** -- An agent creating documentation needs to know only: (a) which directory to write to, (b) to include `title` frontmatter, and (c) to create `_category_.json` + `README.md` when creating new subdirectories.

5. **Nearly everything in the current config is template boilerplate** -- The config needs a full overhaul: project metadata, navbar, sidebars, footer, and removal of template content.

6. **Standardize on `developer-docs`** -- The request text says `develop-docs` but the filesystem has `developer-docs`. Use the existing name.

## Resolved Questions

### Content Scope
- **Project name:** ASH Workbench
- **Deployment:** GitHub Pages (deferred). Will use `gh-pages` branch.
- **Blog:** Removed. Not needed.

### Working Docs
- **Production builds:** Working docs should be **excluded** from production builds. Build-time filtering is needed to strip the `working/` section and its navbar item from production output.
- **Retention:** No automatic pruning. The user will manually graduate working docs (move them into developer-docs or user-docs) when ready.

### Homepage
- **Content:** The homepage should explain what the doc site contains -- a brief overview of the three sections (User Docs, Developer Docs, Working) and what each covers. Not a redirect; an actual landing page.

### Deployment
- **Target:** GitHub Pages via `gh-pages` branch. Deployment pipeline setup is deferred.
- **Base URL:** Will likely need to be set to `/<repo-name>/` for GitHub Pages project sites.

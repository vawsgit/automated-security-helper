# Documentation Authoring Guidance for ASH Workbench

Research document analyzing the ASH Workbench project to produce detailed guidance for organizing and authoring both user-facing and developer-facing documentation.

## Overview

ASH Workbench is a VS Code extension that lets developers run Automated Security Helper (ASH) scans, review findings, triage them (fix/suppress/defer), manage suppressions via `.ash.yaml`, and get AI-assisted analysis of findings — all within the VS Code graphical environment. The project is a monorepo with three subprojects:

- **`vsix/`** — The VS Code extension host (TypeScript, Node.js) that manages the database, spawns ASH CLI processes, handles commands and providers, and communicates with the WebView.
- **`webview/`** — A React 19 single-page application using ShadCN/ui and Tailwind v4 that renders all UI inside VS Code WebView panels (sidebar, editor panel, Kitchen Sink).
- **`docs/`** — A Docusaurus v3.9.2 documentation site with three autogenerated sidebars: User Docs, Developer Docs, and Working (ephemeral, excluded from production builds).

Documentation for this project serves two distinct audiences — end users of the VS Code extension and developers contributing to the codebase. This research investigates what the project does, how it's built, and what documentation already exists, then provides concrete guidance for filling gaps and maintaining quality.

## Feature Inventory

Understanding what the extension actually does is essential for writing accurate documentation. The following is a complete feature inventory derived from reading every source file.

### Core Features (User-Facing)

1. **Project Management** — Each VS Code workspace maps to a project. The extension auto-creates a project record on first activation. Scan history and findings are scoped to the project.

2. **Scan Execution** — Users can scan any directory via the Command Palette (`ASH: Start Scan`). The extension spawns the ASH CLI (`ash --source-dir ... --output-formats sarif`), streams real-time output to an Output Channel, and parses the resulting SARIF report into the database. Only one scan can run at a time. Scans can be cancelled.

3. **Scan History** — A tree view in the sidebar lists all past scans with status icons (completed, failed, cancelled, running). Users can click a scan to view its findings or right-click to delete it.

4. **Scan Targets** — Each directory scanned becomes a "scan target." The dashboard groups findings and scans by target. Users can filter findings by target.

5. **Finding List** — A TanStack React Table shows findings with columns for severity, title, file path, scanner, rule ID, and disposition. Advanced filtering by severity, disposition, scanner, and free-text search. Batch selection is supported.

6. **Finding Detail** — Full detail view with:
   - Header (title, severity badge, disposition badge)
   - Triage controls (Pending/Fix/Suppress/Defer buttons)
   - Description section
   - Code location with clickable file path (navigates to editor)
   - Syntax-highlighted code block with line-range highlighting
   - Triage notes textarea
   - AI Analysis section (analyze button, progress, or results)
   - Suppression panel (view/add/remove suppressions)
   - Previous/Next navigation between findings

7. **Disposition Triage** — Each finding has a disposition: PENDING (default), FIX, SUPPRESS, or DEFER. Setting SUPPRESS is disabled when a finding isn't currently suppressed — users must use the suppression form to create a `.ash.yaml` entry instead.

8. **Suppression Management** — Full lifecycle management of `.ash.yaml` suppression rules:
   - Create suppressions with scope (file+rule, rule everywhere, file all rules), justification, optional line range, optional expiration date
   - View YAML preview before saving
   - Edit existing suppressions (justification, expiration)
   - Remove suppressions
   - Suppression overlay on findings (shows which findings are actively suppressed)
   - Ignore paths display (read-only)
   - Configuration summary (project name, severity threshold, enabled scanners)

9. **AI-Assisted Analysis** — Per-finding AI analysis using Claude Agent SDK:
   - One-click "Analyze with AI" button on finding detail
   - Streaming progress with tool usage display
   - Structured output: explanation, risk assessment (exploitability/impact/likelihood with rationales), suggested fix, references
   - Analysis metadata (model, cost, timestamp, tools used)
   - Analysis persisted to database (survives session restarts)
   - Configurable: provider (Bedrock/Anthropic API), model, budget cap, tool mode (read-only/full), max turns
   - Claude Code settings inheritance (auto-detects `~/.claude/settings.json`)
   - Test connection feature on dashboard

10. **Navigation** — Breadcrumb trail for multi-level navigation (Dashboard → Finding List → Finding Detail). History stack enables back navigation. Sidebar provides compact dashboard with quick-access buttons.

11. **Code Navigation** — Clicking a file path in the finding detail opens the file in the VS Code editor at the relevant line number.

12. **Settings** — Configurable via VS Code Settings:
    - `ashWorkbench.scanRoot` — Default scan directory
    - `ashWorkbench.ashPath` — Path to ASH CLI executable
    - `ashWorkbench.ashMode` — Scan mode (local/container)
    - `ashWorkbench.scanTimeout` — Timeout in seconds
    - `ashWorkbench.defaultSeverityThreshold` — Minimum severity to show
    - `ashWorkbench.llm.*` — All LLM/AI settings (provider, region, model, profile, budget, tool mode, max turns, credential refresh)

13. **Application Reset** — `ASH: Reset Application` command that deletes all data and reloads the window.

14. **Kitchen Sink** — Development-only component showcase (28 demos) accessible via `ASH: Open Kitchen Sink` command.

### UI Contexts

The React WebView app renders in three contexts:

| Context | Where | What it shows |
|---------|-------|---------------|
| `sidebar` | Activity bar sidebar panel | Compact dashboard: quick actions, scan targets, triage progress, severity breakdown, AI status |
| `editorPanel` | Editor area tab | Full UI: dashboard, finding list, finding detail, scan history, scan progress, suppression manager |
| `sink` | Editor area tab (dev only) | Kitchen Sink component gallery |

## User Documentation Guidance

### Audience

End users of ASH Workbench are developers who:
- Work in VS Code daily
- Have ASH CLI installed (or can install it)
- Want to find and fix security issues in their code
- May or may not be familiar with SARIF, security scanners, or suppression workflows
- May or may not have access to an AI provider (Bedrock or Anthropic API)

They care about **how to use the tool**, not how it's built. Documentation should be task-oriented: "I want to scan my code" → here's how.

### Content Guidelines for User Docs

**Lead with the user's goal.** Every page should open with what the user wants to accomplish, not feature descriptions.

```markdown
# Running a Scan

Scan your project to find security issues. ASH Workbench runs the ASH CLI
against your code and imports the results for review.
```

**Use numbered steps for procedures.** Every "how to" should be a numbered list with explicit UI actions.

```markdown
## Start a scan

1. Open the Command Palette (`Ctrl+Shift+P` / `Cmd+Shift+P`).
2. Type **ASH: Start Scan** and select it.
3. Choose a scan target:
   - **Workspace root** — scans the entire workspace
   - **A previous target** — rescans a previously scanned directory
   - **Browse...** — pick any directory
4. The scan starts. Progress appears in the sidebar and in the ASH Output Channel.
```

**Document what users see.** When describing UI elements, use the exact labels, icons, and colors that appear in the interface. Reference the sidebar, Command Palette, editor panel, tree view, and status indicators by their VS Code names.

**Use consistent terminology.** Maintain a terminology table across all user docs:

| Term | Meaning | Never say |
|------|---------|-----------|
| **ASH** | The Automated Security Helper scanning tool (CLI) | "the scanner tool" |
| **ASH Workbench** | This VS Code extension | "the extension", "the plugin" |
| **scan** | One execution of ASH against a directory | "analysis", "check" |
| **finding** | A security issue detected by a scanner | "vulnerability", "issue", "alert" |
| **scanner** | A specific tool ASH runs (bandit, semgrep, checkov, etc.) | "checker", "analyzer" |
| **severity** | Finding importance: Critical, High, Medium, Low, Info | Capitalize consistently |
| **disposition** | Triage status: Pending, Fix, Suppress, Defer | "status", "state" |
| **suppression** | A rule in `.ash.yaml` that marks a finding as intentionally accepted | "exception", "waiver" |
| **scan target** | A directory that has been scanned | "project", "folder" |
| **AI analysis** | Claude-powered explanation and risk assessment of a finding | "AI review", "AI scan" |

**Explain settings with a consistent format.** For the settings reference page, document each setting as:

```markdown
### `ashWorkbench.ashPath`

**Type:** string
**Default:** `"ash"`
**Scope:** User

Path to the ASH CLI executable. If ASH is installed globally and on your PATH,
the default `"ash"` works. Set this to a full path if ASH is installed in a
non-standard location.
```

**Document error states.** Every feature that can fail should have troubleshooting content. Cover:
- Scan fails to start (ASH not found, no workspace)
- Scan fails during execution (timeout, CLI error)
- AI analysis fails (credentials, budget exceeded, network)
- Suppression write fails (file locked, YAML syntax error)

**Don't duplicate ASH CLI documentation.** The ASH CLI is a separate project. Link to its README for CLI installation, scanner details, and SARIF format. Document only what ASH Workbench adds on top.

**Don't document unbuilt features.** The functional design describes features like categories, delta reports, and batch operations that are not yet implemented. Only document what exists in the code today.

### Priority Order for User Docs

Write user documentation in this order (highest impact first):

1. **Getting Started** — Installation + first scan. This is the entry point for all users.
2. **Navigating Findings** + **Finding Details** — The core daily workflow.
3. **Triaging Findings** — Dispositions and notes. The primary action users take.
4. **Settings Reference** — Users will need this immediately to configure ASH path and scan root.
5. **Suppressions** — Important for teams with established workflows.
6. **AI Analysis Setup + Usage** — High-value feature but requires additional configuration.
7. **Troubleshooting** — Build as issues are reported; seed with known failure modes.

### Content Guidelines for Developer Docs

**Show the current state, not the design intent.** The functional and technical design documents reflect early planning. New developer docs should describe what the code actually does today. Reference source files with `file_path:line_number` format.

**Document patterns with examples.** When describing a pattern (e.g., "how to add a new service"), show a concrete example from the existing code, then generalize:

````markdown
## Adding a new service

Services are classes with constructor-injected dependencies and async methods.
They live in `vsix/src/services/`.

**Example:** `FindingsService` receives a Prisma client in its constructor:

```typescript
// vsix/src/services/findings.ts:14
export class FindingsService {
  constructor(private readonly prisma: PrismaClient) {}

  async getFindings(scanId: string, filters?: FindingFilters): Promise<FindingRow[]> {
    // ...
  }
}
```

**To add a new service:**
1. Create `vsix/src/services/<name>.ts`
2. Accept dependencies via constructor (Prisma client, other services)
3. Instantiate in `extension.ts` after database initialization
4. Pass to providers that need it via setter methods
````

**Keep the message protocol doc as the source of truth.** The message protocol is the contract between extension host and WebView. When rewriting `message-protocol.md`, list every message type with its payload shape and which provider/component handles it. Use a code block showing the actual TypeScript union type.

**Document the database schema.** The Prisma schema defines the data model. Document each entity (Project, ScanTarget, Scan, Finding), its key fields, and relationships. Show the migration strategy (raw SQL in transactions, tracked in `_ash_migrations` table).

**Use Mermaid for architecture diagrams.** Docusaurus has Mermaid enabled. Use it for:
- Component dependency graphs
- Message flow sequences
- State machine diagrams (scan lifecycle, view navigation)
- Data flow (CLI → SARIF → parser → database → WebView)

**Document the service inventory.** Create a table of all services with their file path, responsibility, key methods, and dependencies. This is the most useful reference for developers navigating the codebase:

| Service | File | Responsibility | Dependencies |
|---------|------|----------------|-------------|
| `DatabaseService` | `services/database.ts` | PGLite + Prisma init, migrations | None (static) |
| `ScannerService` | `services/scanner.ts` | ASH CLI spawn, scan lifecycle | PrismaClient |
| `FindingsService` | `services/findings.ts` | Finding CRUD, suppression overlay | PrismaClient |
| `AiService` | `services/aiService.ts` | AI analysis orchestration | AiProvider, MCP tools |
| `ClaudeAgentProvider` | `services/claudeAgentProvider.ts` | Claude Agent SDK integration | Settings |
| `AshYamlService` | `services/ashYaml.ts` | `.ash.yaml` file watching, parsing | AshYamlCore |
| `AshYamlWriteService` | `services/ashYamlWrite.ts` | `.ash.yaml` mutation | AshYamlCore |
| `ScanRootService` | `services/scanRoot.ts` | Effective scan root resolution | VS Code settings |
| `ClaudeSettingsDetector` | `services/claudeSettingsDetector.ts` | `~/.claude/settings.json` detection | Filesystem |
| `AdminService` | `services/admin.ts` | Application info and reset | PrismaClient |

**Document what breaks if you're not careful.** The most valuable developer documentation is the "gotchas" section. Key items to document:

1. **Type synchronization** — `vsix/src/models/messages.ts` and `webview/src/types/messages.ts` are manual copies. They must stay in sync. There is no build-time validation.
2. **Fixed Vite output filenames** — `webview/vite.config.ts` produces `assets/index.js` and `assets/index.css` without hashes. The extension host hardcodes these paths in `vsix/src/providers/webviewHtml.ts`. Changing Vite output config without updating the HTML generator breaks the webview.
3. **`acquireVsCodeApi()` singleton** — Called once at module scope in `webview/src/hooks/useVSCodeAPI.ts`. Cannot be called again. Cannot run outside a VS Code webview context.
4. **CSP constraints** — All webviews have a Content Security Policy. No external fonts, images, or scripts. No `eval()`. Nonce-based script/style loading.
5. **`color-scheme: dark` in `index.css`** — Removing this makes native input icons (date picker, search clear) invisible in dark themes.
6. **`@custom-variant dark` in `index.css`** — Removing this breaks all Tailwind `dark:` prefixes in the VS Code WebView.
7. **Panel manager instance state** — `FindingsPanelManager` stores `currentScanId` as an instance variable. The single `handleMessage` listener reads this variable on every call. Adding a second scan context without updating this pattern will cause state bugs.
8. **PGLite ESM import** — PGLite is ESM-only. The extension uses dynamic `import()` at runtime (not static import) because the extension host runs as CommonJS.
9. **Kitchen Sink dev-mode gate** — The `openKitchenSink` command is only registered when `extensionMode === Development`. It will silently not appear in production builds.
10. **Webview copy step** — After building the webview (`webview/dist/`), output must be copied to `vsix/webview-dist/` before the extension can use it. Forgetting this step means the extension loads stale webview code.

## Documentation System Patterns and Conventions

These conventions apply to both user and developer documentation.

### File and Directory Conventions

- **Filenames:** kebab-case only (`running-scans.md`, not `RunningScans.md`)
- **Category indices:** `README.md` with `title: Overview` frontmatter
- **Category metadata:** `_category_.json` in every subdirectory with `label`, `position`, `collapsible: true`, `collapsed: true`
- **Frontmatter minimum:** Every `.md` file needs `title:`
- **Sidebar position:** Only set `sidebar_position` when reading order matters (e.g., Getting Started sequence). Otherwise let alphabetical sorting handle it.
- **Consolidation trigger:** When a flat directory exceeds 6-8 files, create subcategories

### Content Conventions

- **Cross-links:** Relative file paths only (`../user-docs/getting-started/installation.md`), never absolute URL paths
- **Diagrams:** Mermaid preferred. Static images only when Mermaid cannot represent the content (screenshots). Images go in `docs/static/img/`
- **Code blocks:** Always specify language identifier (`typescript`, `json`, `bash`, `yaml`)
- **Admonitions:** Use sparingly — `:::tip`, `:::warning`, `:::danger`, `:::info`, `:::note`. If every other paragraph is an admonition, none stand out.
- **MDX safety:** All `.md` files are compiled as MDX. Bare angle brackets outside code fences will break the build. Use backtick-wrapping for types (`` `Promise<void>` ``), Unicode arrows (`→`, `←`), or HTML entities (`&lt;`, `&gt;`).
- **No marketing language:** Never use "powerful", "seamless", "robust", "cutting-edge"
- **No empty sections:** If a section doesn't apply, omit it entirely rather than leaving "TBD"

### Skill Workflow

Two Claude Code skills automate the documentation workflow:

- **`/user-docs`** — Writes user documentation. Enforces search-before-write, places files in `docs/docs/user-docs/`.
- **`/dev-docs`** — Writes developer documentation. Same search-first pattern, targets `docs/docs/developer-docs/`.

Both skills load detailed guidance files before writing. The guidance files contain the authoritative conventions; the skill files contain the workflow steps.

### Cross-Referencing Between Sections

User docs and developer docs should cross-link when appropriate but never duplicate content:

- User docs should NOT explain how features are implemented — that's developer territory
- Developer docs should NOT duplicate user-facing instructions — link to user docs instead
- The suppression system is a good example: user docs explain how to create a suppression; developer docs explain how `AshYamlWriteService` serializes it to YAML

## Issues and Risks

1. **Type drift between message protocol docs and code** — The message types in `vsix/src/models/messages.ts` are the source of truth. Documentation of the protocol will drift as new specs add messages. **Mitigated:** Auto-generate protocol docs from the TypeScript source (see Resolved Questions #2).

2. **Stale extension-host.md may mislead contributors** — The current version describes a mock-data architecture that no longer exists. A contributor reading this doc before the code would have an incorrect mental model. Priority: rewrite before it causes confusion.

3. **User docs are entirely absent** — There is zero user documentation. Any user who installs the extension has no guidance. This is the highest-impact documentation gap.

4. **Working docs contain valuable content that should be promoted** — Several working documents (prototype research, finding information design, IPA as-built notes) contain insights that should inform published documentation. They should be mined for content, not moved wholesale.

5. **No screenshots or visual aids in user docs** — User documentation would benefit greatly from screenshots of the sidebar dashboard, finding list, finding detail, and suppression form. Use `<!-- TODO: screenshot of [feature] -->` HTML comment placeholders while authoring; capture actual screenshots into `docs/static/img/user-docs/` once the UI stabilizes.

## Key Takeaways

1. **User documentation is the highest-priority gap.** It is completely empty. Start with Getting Started (installation + first scan) and the core finding-review workflow.

2. **Developer documentation has a solid skeleton but is partially stale.** The build pipeline, testing, documentation system, and Kitchen Sink docs are thorough and accurate. The extension host and message protocol docs need full rewrites to reflect the current service-based architecture.

3. **Both audiences need the suppression system documented.** Suppressions are the most complex feature from both user and developer perspectives. User docs should explain the workflow; developer docs should explain the implementation.

4. **AI analysis is the newest and least-documented feature.** It spans the extension host (Claude Agent SDK, MCP tools, structured output) and WebView (streaming progress, analysis panel). Both user and developer docs should cover it.

5. **The documentation system itself is well-designed.** Autogenerated sidebars, Mermaid support, MDX compilation, production filtering of working docs, and search-before-write skills provide a solid foundation. The tooling is ready; the content needs to be written.

6. **Consistency between docs and code is the ongoing challenge.** As the project evolves through numbered specs, documentation must be updated alongside code. The `/dev-docs` and `/user-docs` skills help, but only if invoked. Consider adding documentation updates to the spec/plan/tasks workflow.

## Resolved Questions

1. **Screenshots: add after UI stabilizes, use placeholders now.** The UI is actively being developed (branch `022-finding-analysis` has significant WebView changes). Screenshots taken now would be outdated within days. **Decision:** Add `<!-- TODO: screenshot of [feature] -->` placeholders in user docs as they're written. Capture actual screenshots once the UI stabilizes. This keeps the docs structurally complete while avoiding maintenance churn.

2. **Message protocol docs: auto-generate from TypeScript source.** The message types in `vsix/src/models/messages.ts` are the source of truth. Manual documentation will drift as new specs add messages. **Decision:** Yes — build a script or use `typedoc` to extract the `ExtToWebviewMessage` and `WebviewToExtMessage` discriminated unions and produce a markdown table. This should be a development task, not a documentation task.

3. **Spec system (`.specify/`): exclude from developer docs.** The specification toolkit is a development process tool, not part of the product architecture. **Decision:** Do not document `.specify/` in developer docs. Remove `specification-system.md` from the recommended topic structure. The `.specify/` directory is self-documenting via its templates and constitution.

4. **AI analysis credentials: reference external documentation.** The setup requires either AWS Bedrock access or an Anthropic API key. **Decision:** User docs should reference external AWS and Anthropic documentation for credential setup, not duplicate those instructions. The `ai-analysis/setup.md` page should cover only ASH Workbench-specific configuration (which provider setting to choose, where to enter the profile/key, budget and tool mode settings) and link out for the "how to get credentials" part.

5. **Functional and technical design documents: keep in developer docs.** They reflect design intent rather than as-built reality. **Decision:** Keep them in `developer-docs/architecture/software-design-specification/` for now. They document the "why" behind design decisions and will be valuable reference material if the application is extended. Add a note to the `README.md` in that directory clarifying that these documents reflect original design intent and may not match current implementation in all details.
